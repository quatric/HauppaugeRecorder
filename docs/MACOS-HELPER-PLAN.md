# macOS TV helper: plan and notes (work in progress)

Goal: `tv-capture-macos`, a helper with the protocol of [TVHELPER.md](TVHELPER.md) for the Hauppauge WinTV HVR-950Q
(USB 2040:7200) on macOS, where Hauppauge has no driver. It has to do in user space, over libusb (already vendored),
what Linux's `au0828` (USB bridge), `au8522` (video decoder) and `xc5000` (tuner) drivers do.

## Licence: needs a decision before this ships

The three Linux drivers are GPL-2.0-or-later. Everything below is derived from them, so the files that carry it are
GPL, and so is a helper binary built from them. Kept apart on purpose:

* `src/au8522_regs.h`, `src/au8522_init.h` are generated by `scripts/gen-au8522.py` from the kernel source and say so.
* the helper is a separate program that the app only talks to over pipes, so the app itself is not linked with it.
* the project has no licence of its own yet (only vendored third-party ones); decide this before releasing.
* the tuner firmware `dvb-fe-xc5000-1.6.114.fw` (12401 bytes, linux-firmware) is "Redistributable" under Xceive's own
  terms: do not bundle it. The helper should look for it next to itself, in `~/Library/Application Support/HauppaugeRecorder`
  and in `$XC5000_FW`, and say where to get it when it is missing.

## What the Linux drivers do (all verified in the sources)

**Bridge registers**: vendor control transfers on endpoint 0. Read: `bmRequestType 0xC0, bRequest 0, wValue 0,
wIndex reg`, 1 byte. Write: `0x40, bRequest 1, wValue = value, wIndex = reg`.

**I2C through the bridge** (`au0828-i2c.c`): 0x200 trigger (write 0x01, read 0x20, hold 0x40), 0x201 status (read done
0x01, no read ack 0x02, write done 0x04, no write ack 0x08, busy 0x10), 0x202 clock divider (250 kHz 0x07, 20 kHz 0x40),
0x203 destination address (7-bit << 1), 0x205 write FIFO, 0x209 read FIFO, 0x2ff multibyte mode = 1. Writes go four
bytes per strobe (trigger with HOLD until the last). The xc5000 needs the 20 kHz divider except for 64-byte firmware
writes (250 kHz). Devices (7-bit): au8522 0x47, xc5000 0x61, EEPROM 0x50.

**Board setup for the HVR-950Q** (`au0828-cards.c`): REG_003 = 0x02, REG_002 = 0xB0 (outputs); REG_001 = 0, REG_000 = 0,
sleep 50 ms; REG_000 = 0x80, sleep 50 ms; REG_001 = 0x02, REG_000 = 0xA0, sleep 250 ms. Tuner reset (the xc5000 asks for
it while loading firmware): clear bit 1 of REG_001, sleep 10 ms, set it, sleep 10 ms.

**au8522** registers over I2C: write = 3 bytes `[(reg >> 8) | 0x80, reg & 0xff, value]`; read = write 2 bytes
`[(reg >> 8) | 0x40, reg & 0xff]` then read 1. After probing: register 0x106 = 1 (opens the I2C gate to the tuner).
Streaming on: register 0x0A4 = 0x01, 10 ms, `au8522_video_set()`, `set_audio_input()` (all in the generated
`au8522_init.h`). HVR-950Q inputs: TV = `AU8522_COMPOSITE_CH4_SIF` with `AU8522_AUDIO_SIF`; composite =
`AU8522_COMPOSITE_CH1`; S-Video = `AU8522_SVIDEO_CH13` (both with no audio). Only NTSC-M and PAL-M are supported by the
decoder: no PAL-B/G.

**xc5000** (16-bit registers over I2C): write `[reg_hi, reg_lo, val_hi, val_lo]`, then poll register 0x09 (BUSY) until 0.
Firmware = a sequence of records: a 16-bit length N (0x0000 = reset the tuner via the bridge GPIO, 0x8000|ms = wait,
0xFFFF 0xFFFF = end), then N bytes sent as I2C writes of at most 64 bytes, each prefixed by the first two bytes of the
record. After upload: sleep 20 ms, register 0x00 (INIT) = 0 (self-calibration), sleep 100 ms, check PLL register 0x806c
is <= 63, register 0x0D (SIGNALSOURCE) = 1 (cable). Product id register 0x08 reads 0x2000 when no firmware is loaded.
To tune NTSC: register 0x0D = 1 cable / 0 air; register 0x01 VIDEO_MODE = 0x8020 and 0x02 AUDIO_MODE = 0x0400 (M/N
NTSC BTSC); register 0x0B OUTPUT_AMP = 0x09; register 0x10 FINERFREQ = picture carrier in Hz / 15625; wait 20 ms and
check the PLL again (reload the firmware if > 63).

**Video and VBI** (`au0828-video.c`): `libusb_set_interface_alt_setting(interface 0, 5)`, the isochronous IN endpoint of
that setting (packet size from the descriptor, multiplier included). Start: audio control register 0x50C = 0x01 (I2S),
0x103 = 0, 0x106 = 0, x position 0x110/0x111 = 0, 0x114/0x115 = width*2 (low, high), y position 0x112/0x113 = 0,
0x116/0x117 = height/2 + 2, then 0x100 = 0xB3 (stream on); stop = 0x100 = 0. 12 transfers of 128 packets.
Each packet: byte 0 flags, 4 bytes of header, payload. If flags & 0x80 a field starts: 4 more header bytes; flags & 0x40
means the top field, which also closes the frame in progress and starts the next. The payload of a field is first
`vbi_width * vbi_height * 2` = 1440 bytes of VBI (720 samples; the sample is the second byte of each pair; one line per
field, at 13.5 MHz, lines 21 and 284), then the picture lines of that field, 1440 bytes (UYVY) each, interleaved into
the frame (top field on even lines, bottom on odd). 720x480.

**Audio** is not in this stream: the decoder turns the tuner's sound into I2S and the bridge presents it as a USB Audio
Class device, which macOS handles natively. The helper only captures from it with Core Audio (AudioQueue), after
interface 0 is claimed with libusb (the audio interfaces stay with the system).

## Open question that needs real hardware

Which of the two fields in the USB stream carries line 21 and which line 284 (the kernel assumes the field flagged 0x40,
which comes first, is field 1). On Windows the first VBI buffer of every frame was the line-284 field. Check with
`--probe` before trusting the order.
